# Native Family Spaces

**Spaces** in the bottom bar, or Home, opens family Spaces and the current account's invitation inbox. The client can create a private family Space, copy its own account ID, review/accept/decline an intended-account invitation, and manage owner-created invitations with explicit revocation confirmation. Opening family tasks carries the selected Space ID; an unavailable selection cannot silently fall back to another family.

The existing account repository owns authentication and session isolation. Runtime validation checks private/family scope, roles, recipient/Space identity, expiry ordering and bounded pagination. A page cannot return its requested cursor as its next cursor. Backend services still authorize every operation; a displayed role or invitation is not an authority grant.

Unknown outcomes retain the exact command, payload and creation key for explicit retry. Forms and scope changes are locked during that uncertainty. Accept, decline and revoke retain the selected invitation identity; notices report the canonical outcome rather than claiming every replay is pending. Drafts and retry state survive activity recreation in the ViewModel, not process death or deliberate workspace exit.

Refresh revalidates the open Space before loading unrelated inbox data. A denied Space therefore clears its protected details even when that inbox is unavailable. Account changes and session loss clear protected state. DTO fields use the same release shrinker protection as the other native clients.

The selected Space now provides a bounded private member roster, exact permission-checked removal review and member/admin self-leave. Commands retain their actor, target, membership ETag and request key across unknown outcomes. A stale precondition clears the roster and requires fresh review; a confirmed leave clears the private family view. An owner cannot depart before a separately accepted ownership transfer; owner-only role changes use the separate review described below. A former member returns only through the existing invitation review; the removal/leave confirmation says so and that earlier tasks and reminders stay unavailable. The client has no separate rejoin command.

Eleven offline screen tests passed, including membership confirmations and measured 320 dp / 200% dialogs. The fixture applies the real system font setting before activity launch and measures the dialog's actual text scale; a composition-only override was insufficient. The clipboard case still checks its payload with a test double, not OS integration. A separately executed live native membership journey also passed against the approved local services, covering removal, self-leave, denied access and recreation. ## Group Spaces and Find Groups

Built for [T22](../../../../../../../../../../docs/TASKS.md#spaces). Creating a Space offers Family, Group and Solo; a group gets an optional description and a Private or Public choice with an explanation. Lists and the selected Space show the type and visibility; groups get the same members and invitation controls as families. Validation accepts `public` only for a group and limits descriptions to 280 characters.

**Find groups** (`GroupScreen`, `GroupViewModel`, `GroupRepository`) searches public groups and shows name, description and member count. People ask to join with an optional note, retry an unconfirmed request with the same key, withdraw it, and see their requests. **Group access**, opened by an owner or admin from a selected group, lists waiting requests to approve or decline. Only an owner can switch the group between private and public after a confirmation. The join-request endpoints live in a separate `GroupApi`; role changes extend `SpaceApi`. Space owners can edit descriptions for every Space type, with public/private labels, a 280-character limit and immutable original-intent retries. JVM tests cover description-only and name-only payloads, unchanged retry identity, local text validation, reload behavior and response confirmation.

## Space Roles

Built for T13 under [DEC-018](../../../../../../../../../../docs/DECISIONS.md#accepted-decisions), which remains provisional. Spaces and rosters accept owner, admin and member, while a roster still requires exactly one owner. Only the owner can make another current member an admin, or an admin a member, in family and group Spaces. The confirmation names the Space, person and account ID and explains the changed permissions; an unknown outcome retains the exact role, key and reviewed ETag for explicit retry. A stale review clears the roster. Confirmed promotion/demotion shows the person's new role and reloads the roster and Space list.

Admins can invite people as members, revoke waiting invitations, remove ordinary members and leave themselves. They cannot remove the owner or another admin, change roles or Space settings, switch visibility, or offer ownership. Owners can remove admins and offer them ownership. Group access reads the current Space role before loading requests: admins see only request review and never call the owner-only settings endpoint. The directory labels their role explicitly.

New JVM tests in `SpaceRepositoryTest`, `SpaceViewModelTest` and `GroupRepositoryTest` cover admin validation, the one-owner and unknown-role guards, exact role transport and response matching, permission limits, confirmation and unchanged retry intent, success notices/reloads, admin directory entries and settings-free request review. `SpaceScreenTest` keeps its 15 earlier methods and assertions (three constructor arguments were added for the reviewed Space snapshot) and adds two device tests: `roleActionsFollowTheViewersRoleAndConfirmOnlyTheReviewedMember` (which role and removal actions the owner and an admin see, and that confirming sends only the reviewed member) and `roleReviewKeepsExactDetailsAndActionsAtLargeText` (320 dp, measured font scale 2.0, details reachable, both actions visible). All 17 passed offline on the API 36 emulator on 2026-10-01. Two more, `coupleChoiceAndPartnerStatusStayReadableAtLargeText` and `spaceSettingsDescriptionCountsCharactersAndKeepsSaveReachableAtLargeText`, cover the couple choice and status and the settings description at 320 dp and 200% text; all 19 passed.

## Couple Spaces

Built for [T12](../../../../../../../../../../docs/TASKS.md#approved-requirements-not-built-yet) under [DEC-017](../../../../../../../../../../docs/DECISIONS.md#accepted-decisions) (provisional). Creating a Space also offers Couple (test tag `space-type-couple`), with the note "Only you and one partner you invite". Lists and the selected Space say "Couple Space"; when the member list is open, a couple shows "Waiting for your partner" or "With" and the partner's name, and the owner's invitation section explains that a couple is for two people with one waiting invitation at a time. No extra network call is made for this. Validation accepts `couple` only as private. The server's `COUPLE_FULL` and `COUPLE_INVITATION_PENDING` messages are shown as they are. Evidence: three JVM tests (`coupleCreationKeepsTypeAndPrivateVisibility`, `coupleResponsesRejectPublicVisibility`, `coupleCreationSendsTypeAndShowsPartnerInvitationNotice`); no device test was added, so the 15 offline Space screen tests are unchanged.

## Ownership Transfer

The existing Space commands now include `OfferOwnership` and `RespondOwnership`, with strict participant, Space, lifecycle and exact-response validation. Offers bind the reviewed member and original key/ETag; responses retain the exact reviewed offer. The member panel exposes owner offers, recipient acceptance/decline and sender withdrawal with an explicit exact-person confirmation and separate expiry/effect facts. Uncertain outcomes lock competing actions until an explicit original retry. Stale reviews require reload; recent-sign-in errors do not silently submit again.

After a confirmed outcome, the ViewModel clears old role-sensitive state and reloads current membership before enabling controls. Historical accepted receipts never directly promote a cached role or grant old task history. The former owner can leave only after the current server roster confirms their ordinary-member role.
